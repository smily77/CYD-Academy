## 🎯 Was ist die CYD-Academy?

Die **CYD-Academy** ist eine umfassende **Lernplattform für ESP32 Display-Programmierung** mit dem CYD (Cheap Yellow Display). Sie bietet:

### Philosophie & Ziele

1. **Lernen durch Praxis** - Nicht nur Code, sondern Verständnis vermitteln
2. **Von Basic bis Advanced** - Strukturierter Lernpfad
3. **Ausführliche Dokumentation** - Jedes Beispiel erklärt das "Warum", nicht nur das "Wie"
4. **Wiederverwendbarer Code** - Best Practices und professionelle Struktur
5. **Hardware-Flexibilität** - Unterstützung verschiedener CYD-Varianten und Erweiterungen

### Zielgruppen

- **Anfänger**: Erste Schritte mit ESP32 Display-Programmierung
- **Fortgeschrittene**: Komplexe Projekte mit Sensoren, Kommunikation, Echtzeit-Daten
- **Profis**: Master Class mit vollständigen Arcade-Spielen als Referenz

### Inhalte

1. **Examples (examples/)**: 21+ strukturierte Lernbeispiele
   - Basics: Display, Touch, Grafik
   - Intermediate: WiFi, Sensoren, I2C
   - Advanced: ESP-NOW, Multi-Threading, komplexe Visualisierungen

2. **Arcade Games (arcade-games/)**: 14 vollständige Spiele als Master Class
   - Pong, Snake, Breakout, Space Invaders, Asteroids, Frogger, Tetris
   - CYD_Games Library mit wiederverwendbaren Klassen

3. **Libraries (libraries/)**: Wiederverwendbare Komponenten
   - CYD_Games: Game Engine Komponenten

## 📚 Display-Konfiguration: CYD_Display_Config.h

### Externe Library: MyLGFXConfigs

Die CYD-Academy verwendet die **MyLGFXConfigs Library** (externes Repository) für Display-Konfiguration:

```
Repository: https://github.com/[username]/MyLGFXConfigs
Installation: Arduino/libraries/MyLGFXConfigs/
```

### Was enthält CYD_Display_Config.h?

```cpp
#include <LovyanGFX.hpp>

// ========================================
// LGFX Klassen-Definition
// ========================================
// Hier wird der LGFX-Konstruktor definiert:
// - Display-Typ (ILI9341, ILI9488, etc.)
// - SPI-Pins (MOSI, MISO, SCK, CS, DC, RST)
// - Touch-Controller (XPT2046)
// - Display-Rotation und Kalibrierung

class LGFX : public lgfx::LGFX_Device {
  lgfx::Panel_ILI9341 _panel_instance;
  lgfx::Bus_SPI _bus_instance;
  lgfx::Touch_XPT2046 _touch_instance;

public:
  LGFX(void) {
    // Detaillierte Panel-Konfiguration
    auto cfg = _panel_instance.config();
    cfg.pin_cs = 15;
    cfg.pin_rst = -1;
    // ... weitere Konfiguration

    // Bus-Konfiguration
    auto bus_cfg = _bus_instance.config();
    bus_cfg.pin_mosi = 13;
    bus_cfg.pin_miso = 12;
    bus_cfg.pin_sclk = 14;
    // ... weitere Konfiguration

    // Touch-Konfiguration
    auto touch_cfg = _touch_instance.config();
    touch_cfg.pin_cs = 33;
    // ... weitere Konfiguration
  }
};

// ========================================
// GPIO Pin-Definitionen
// ========================================
// Standard-Pins für CYD Hardware-Erweiterungen

// RGB LED
#define rgbLedR 4
#define rgbLedG 16
#define rgbLedB 17

// Photoresistor (LDR)
#define photoPin 34

// I2C für Sensoren & Erweiterungen
#define extSDA 22
#define extSCL 27

// Serielle Schnittstelle (UART2) für GPS, Sensoren, etc.
#define extRxD 16    // GPIO 16 - Empfangen von externen seriellen Geräten
#define extTxD 17    // GPIO 17 - Senden zu externen seriellen Geräten

// WICHTIG: Diese Pins werden IN CYD_Display_Config.h definiert!
// Code-Beispiele dürfen diese Pins NICHT neu definieren, sondern müssen
// die Werte aus der Config-Datei verwenden (genau wie extSDA/extSCL).
//
// Verwendung der seriellen Schnittstelle:
// Serial2.begin(9600, SERIAL_8N1, extRxD, extTxD);  // z.B. für GPS mit 9600 Baud
//
// Typische Anwendungen:
// - GPS-Module (NMEA, 9600 Baud)
// - Serielle Sensoren (PM2.5, CO2, etc.)
// - Modbus/RS485 (mit Pegelwandler)
// - Debug-Ausgabe zu zweitem Display/Logger
//
// WICHTIG: Falls RGB-LED auf GPIO 16/17 verwendet wird (manche CYD-Varianten),
// alternative Pins verwenden: GPIO 25, 26, 32, 33

// Optional: Interrupt Pin für Sensoren
#ifdef HAS_INTERRUPT_PIN
  #define extIrqPin 35  // Beispiel
#endif

// ========================================
// Hardware-Konfiguration (Optional)
// ========================================
// Verschiedene Steuerungs-Optionen

// Option 1: GPIO-Buttons (direkt am ESP32)
#ifdef gpioSwitch
  #define tasteA 17
  #define tasteB 5
  #define tasteC 16
  #define tasteD 18
#endif

// Option 2: I2C-Buttons (PCF8574 Portextender)
#ifdef i2cSwitch
  #define tasteA 0
  #define tasteB 1
  #define tasteC 2
  #define tasteD 3
  #define pcfAddress 0x20
  #define switchInterrupt 22  // Optional
#endif

// Option 3: Rotary Encoder
#ifdef gpioEnc
  #define encA 17
  #define encB 5
  #define encSW 16
#endif
```

### Warum diese Struktur?

**Flexibilität für verschiedene CYD-Varianten**:
- CYD 2.8" (320x240, ILI9341)
- CYD 3.5" (480x320, ILI9488)
- Zukünftige Varianten

**Hardware-Erweiterungen unterstützen**:
- Sensoren über I2C (extSDA/extSCL)
- RGB LEDs für visuelle Effekte
- Photoresistor für Auto-Brightness
- Verschiedene Input-Methoden (Touch, Buttons, Encoder)

**Zentralisierte Konfiguration**:
- Keine Hardcoded-Pins in Beispielen
- Ein Ort für Display-Setup
- Einfache Anpassung für neue Hardware

## 🔒 Credentials-Verwaltung: Credentials.h

### Problem: Secrets auf GitHub

WiFi-Passwörter, API-Keys und andere Credentials dürfen **NICHT** öffentlich auf GitHub landen!

### Lösung: Credentials.h (nicht im Repository)

#### 1. Beispiel mit Credentials.h

```cpp
// Im Arduino-Sketch (z.B. 07_WiFiClock.ino):
#include <CYD_Display_Config.h>
#include "Credentials.h"  // WiFi-Zugangsdaten

// WICHTIG im Header-Kommentar des Sketches:
// * WICHTIG: Erstelle eine Datei "Credentials.h" im gleichen Verzeichnis mit:
// *   const char* ssid = "DeinWiFiName";
// *   const char* password = "DeinWiFiPasswort";

void setup() {
  WiFi.begin(ssid, password);
  // ...
}
```

#### 2. Credentials.h Datei-Struktur

Benutzer erstellt **lokal** eine `Credentials.h` Datei:

```cpp
// Credentials.h (NICHT ins Repository committen!)
#ifndef CREDENTIALS_H
#define CREDENTIALS_H

// WiFi Credentials (als const char* Variablen)
const char* ssid = "MeinWiFi";
const char* password = "MeinSuperGeheimesPasswort123";

// Alternative: Mit Großbuchstaben (beide Varianten sind OK)
// const char* WIFI_SSID = "MeinWiFi";
// const char* WIFI_PASSWORD = "MeinSuperGeheimesPasswort123";

// API Keys
const char* OPENWEATHER_API_KEY = "abc123def456...";
const char* TIMEZONE_API_KEY = "xyz789...";

// MQTT Broker
const char* MQTT_SERVER = "192.168.1.100";
const int MQTT_PORT = 1883;
const char* MQTT_USER = "homeassistant";
const char* MQTT_PASSWORD = "mqtt_password";

// Andere Secrets
const char* DEVICE_ID = "CYD-001";

#endif
```

#### 3. .gitignore eintragen

```gitignore
# Credentials (niemals committen!)
**/Credentials.h
Credentials.h
```

#### 4. Template für Benutzer

Im README des Beispiels:

```markdown
## WiFi-Konfiguration

Erstelle eine Datei `Credentials.h` im gleichen Ordner wie das .ino:

```cpp
const char* ssid = "DeinWiFiName";
const char* password = "DeinWiFiPasswort";
```

Wichtig: Nutze `const char*` Variablen (nicht `#define`).
```

### Best Practice für neue Beispiele

1. **Include Credentials.h direkt** - Nutze `#include "Credentials.h"` im Sketch
2. **Header-Kommentar erklärt** - Im Sketch-Header steht, wie Credentials.h aussehen muss
3. **README erklärt Setup** - Schritt-für-Schritt Anleitung für Credentials.h
4. **Beispiel-Template in README** - Copy-Paste-fertig mit `const char*` Variablen
5. **Niemals echte Credentials committen** - Auch nicht in Kommentaren!
6. **Nutze const char*** - NICHT `#define` für Credentials (WiFi-Library erwartet const char*)

## 🎨 Beispiel-Erstellung: Best Practices

### Namenskonvention

**WICHTIG - Arduino IDE Anforderung**:
Die Arduino IDE erfordert, dass die `.ino` Datei in einem **gleichnamigen Verzeichnis** liegt!

```
Format: [Nummer]_[Beschreibung]/[Nummer]_[Beschreibung].ino

Beispiele:
- 01_HelloWorld/01_HelloWorld.ino          ✅ RICHTIG
- 17_Lightning_Sensor/17_Lightning_Sensor.ino  ✅ RICHTIG
- 20_Air_Quality_CCS811/20_Air_Quality_CCS811.ino  ✅ RICHTIG

FALSCH:
- 01_HelloWorld/HelloWorld.ino             ❌ Dateiname passt nicht
- HelloWorld.ino                            ❌ Kein Verzeichnis
- sketches/01_HelloWorld.ino               ❌ Falsches Verzeichnis
```

**Warum?** Die Arduino IDE kann eine `.ino` Datei nur öffnen, wenn:
1. Sie in einem Verzeichnis liegt
2. Das Verzeichnis **exakt** den gleichen Namen hat wie die `.ino` Datei (ohne Extension)

**Nummerierung**:
- `01-10`: Basics (Display, Touch, Grafik)
- `11-16`: Intermediate (Animationen, Charts, Kommunikation)
- `17-25`: Advanced (I2C Sensoren, komplexe Visualisierungen)
- `26+`: Expert (Multi-Threading, AI, etc.)

**Untervarianten**: Verwende Buchstaben (z.B. `13b_Racing_Track_Obstacles`)

```

## 🎯 Code-Qualität & Standards

### Display-Verwendung

```cpp
// RICHTIG: LGFX aus CYD_Display_Config.h verwenden
#include <CYD_Display_Config.h>
LGFX lcd;

void setup() {
  lcd.init();
  lcd.setRotation(0);
  // ...
}
```

```cpp
// FALSCH: LGFX-Klasse direkt im Sketch definieren
#include <LovyanGFX.hpp>
class LGFX : public lgfx::LGFX_Device {
  // ... 77 Zeilen Boilerplate-Code
};
LGFX lcd;
```

**Warum?**
- Flexibilität für verschiedene CYD-Varianten
- Zentralisierte Konfiguration
- Keine Code-Duplikation
- Einfachere Updates

### I2C-Verwendung

```cpp
// RICHTIG: Pins aus CYD_Display_Config.h verwenden (NICHT neu definieren!)
#include <CYD_Display_Config.h>

void setup() {
  Wire.begin(extSDA, extSCL);  // extSDA und extSCL kommen aus Config
}
```

**NICHT** Pins hardcoden oder neu definieren:
```cpp
// ❌ FALSCH: Hardcoded
Wire.begin(22, 27);

// ❌ FALSCH: Neu definieren (überschreibt Config!)
#define extSDA 22
#define extSCL 27
Wire.begin(extSDA, extSCL);
```

### Serielle Schnittstelle (UART2) Verwendung

```cpp
// RICHTIG: Pins aus CYD_Display_Config.h verwenden (NICHT neu definieren!)
#include <CYD_Display_Config.h>

void setup() {
  Serial2.begin(9600, SERIAL_8N1, extRxD, extTxD);  // Pins aus Config
}
```

**NICHT** Pins hardcoden oder neu definieren:
```cpp
// ❌ FALSCH: Hardcoded
Serial2.begin(9600, SERIAL_8N1, 16, 17);

// ❌ FALSCH: Neu definieren (überschreibt Config!)
#define extRxD 16
#define extTxD 17
Serial2.begin(9600, SERIAL_8N1, extRxD, extTxD);
```

### Interrupt-Pins (Optional)

Für Sensoren mit Interrupt-Support:

```cpp
// Check ob Interrupt-Pin definiert ist
#ifdef extIrqPin
  #define IRQ_PIN extIrqPin
  #define USE_INTERRUPT
#else
  #define IRQ_PIN -1  // Kein Interrupt verfügbar
#endif

void setup() {
  #ifdef USE_INTERRUPT
    pinMode(IRQ_PIN, INPUT_PULLUP);
    attachInterrupt(digitalPinToInterrupt(IRQ_PIN), myISR, FALLING);
  #endif
}

void loop() {
  #ifdef USE_INTERRUPT
    // Interrupt-basiert
    if (interruptFlag) {
      handleData();
    }
  #else
    // Polling-Modus als Fallback
    if (millis() - lastPoll >= 100) {
      checkSensor();
      lastPoll = millis();
    }
  #endif
}
```

**Wichtig**: Automatischer Fallback auf Polling wenn kein Interrupt-Pin!

## 🔄 Git Workflow

### Branch-Strategie

- `main`: Stabile, getestete Beispiele
- `claude/[feature-name]`: Feature-Branches für neue Beispiele
- Nach Review: Merge in `main`

### Commit-Message Format

```
[TYPE]: Kurzbeschreibung (max 50 Zeichen)

Ausführlichere Beschreibung (max 72 Zeichen pro Zeile):
- Bullet Point 1
- Bullet Point 2

Features:
- Feature 1
- Feature 2

Technologie:
- Tech Detail 1
- Tech Detail 2
```

**Types**:
- `ADD`: Neues Beispiel oder Feature
- `FIX`: Bugfix oder Korrektur
- `UPDATE`: Verbesserung bestehenden Codes
- `DOCS`: Dokumentation
- `REFACTOR`: Code-Umstrukturierung ohne Funktionsänderung

**Beispiel**:
```
ADD: Beispiel 21 - 3D-Gestensensor MGC3130

Neues Beispiel für berührungslose Gestensteuerung.

Features:
- 3D-Positionserkennung (X, Y, Z)
- 6 Gesten-Typen (Swipe, Kreis)
- Touch-Elektroden (5x kapazitiv)
- AirWheel für Rotations-Steuerung

Technologie:
- E-Field Sensing (Elektrisches Feld)
- SparkFun MGC3130 Library
```

## 🎓 Lern-Philosophie der Academy

### "Verstehen, nicht nur Kopieren"

Die CYD-Academy vermittelt **Wissen**, nicht nur Code:

1. **Warum funktioniert es?** - Physikalische/mathematische Grundlagen
2. **Wie funktioniert es?** - Schritt-für-Schritt Code-Erklärung
3. **Was kann ich damit machen?** - Erweiterungsideen und Projekte
4. **Was sind Alternativen?** - Vergleiche mit anderen Technologien

### README-Struktur erklärt das "Warum"

Ein typisches README hat:

- **Features**: Was macht das Beispiel? (Das "Was")
- **Hardware**: Was brauche ich? (Das "Womit")
- **Technischer Hintergrund**: Wie funktioniert die Technologie? (Das "Warum")
- **Code-Struktur**: Wie ist der Code aufgebaut? (Das "Wie")
- **Troubleshooting**: Was kann schiefgehen? (Das "Falls")
- **Erweiterungen**: Was kann ich daraus machen? (Das "Weiter")

### Praktische Beispiele, nicht abstrakte Theorie

- Jedes Beispiel ist **lauffähig** und **sinnvoll**
- Visualisierungen sind **professionell** (nicht nur Serial.println)
- Touch-Interaktion wo möglich
- Realistische Anwendungsfälle
